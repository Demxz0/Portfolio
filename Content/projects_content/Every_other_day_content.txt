Overview
Every Other Day is a 2D Arabic life-balance sim made in Godot for the Nesto game jam (theme: "The world changes slowly"), in 7 days with a team of 2 — me and Leen. You play someone balancing life tasks like work, study, and hobbies; ignore one area too long and it drags you down. The idea came from watching my own and other people's lives constantly trying to balance everything.

My Role and Responsibilities
All game logic was mine — stats, tasks, events, and the data-driven notebook system. Leen handled art and polish.

Process
The idea was inspired by 60 Seconds, though Leen hadn't played it — looking back, building a whole game around a reference only one of us knew was a mistake.

I wanted the notebook feedback (like in 60 Seconds) to feel like it had endless outcomes, so I asked AI how these systems actually work under the hood. The answer: it's not endless code paths, it's a notebook broken into sections, each pulling a line from a data table based on the player's state.

I built three data tables:

Stats (Energy, Mood, Time) — 5 condition levels each, one sentence per level
Life aspects (Study, Worship, Sports, Programming, Cleaning, Learning language) — good/bad sentence each
Events — random yes/no events that affect one or more aspects

I also built Tasks and Events as script classes, each holding an array of entries with their own ID and variables.

Breakdown

Data tables: stats, life aspects, events (CSV-based)
DataLoader script to import the CSVs
Tasks/Events classes as structured arrays
Notebook UI pulling feedback per day

Challenges and Problems Solved

Picked the 6 life aspects based on my own routine, which made them too specific and less relatable for most players
Had trouble sizing a Scroll node so notebook text fit horizontally
The scope was too big for a 7-day jam given the systems involved

Decisions
Leen suggested adding visual stat bars; I decided against it on purpose, wanting the player to infer their state from the writing instead of a clear bar, to keep the challenge in place. Wanted drawn visual feedback like 60 Seconds too, but ran out of time.

Feedback
Leen wanted visible stat bars — I chose not to add them for gameplay reasons (see Decisions). After submission, the judges said the concept and gameplay actually suit mobile better than PC — I agreed, and think it could work for web too.

How I Used AI
Used AI to understand how "many-outcome" narrative games are structured, which led directly to the data-table design. Also let AI write code without reviewing it closely while busy elsewhere — while writing this portfolio, I found the DataLoader and CSVs I built were never actually connected; the game was quietly running on hardcoded sentences in the main script the whole time.

Lessons Learned

Scope the idea to fit the timeline
Don't build around a reference only one teammate knows
Learned how "infinite outcome" games are really built
Design for the player/audience, not just personal experience
Manage time even when life gets busy
Never let AI drive the code unreviewed — know your own architecture
Pick the platform that fits the gameplay
